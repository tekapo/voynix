# Voynix のプレイリストを Echo（Alexa）で再生する（家の中のネットワークだけで）

[English](./echo-lan.md)

上級者向けの任意機能です。「アレクサ、*〈呼び出し名〉* で、ドライブをかけて」と言うと、Echo が Voynix のそのプレイリストを、
**家の中のネットワーク経由で、Mac から直接**取得して再生します。インターネットには何も公開せず、Alexa のスキルが
Mac に接続することもありません。

既定ではオフで、準備が要ります（ドメイン名、証明書、Echo 用の DNS、ポートの転送、自分用の Alexa スキル）。
このページに、手順を全部書いています。

## しくみ

```
あなた ──▶ Echo ──▶ Alexa クラウド ──▶ あなたのスキル（署名つき URL を作って返す）
                                          │
Echo ◀────────────────────────────────────┘
Echo ──(DNS)──▶ Mac の dnsmasq ──▶ Mac の LAN 内 IP
Echo ──(HTTPS、443番)──▶ Mac ──(pf)──▶ Voynix（8443番）  ──▶  GET /play?list=…&i=…&seed=…&exp=…&sig=…
```

- スキルは、言われたプレイリスト名を `/play?list=<名前>&i=<番号>&seed=<種>&exp=<期限>&sig=<HMAC>` に変えて返します。
  署名は、Voynix と共有するシークレットで作ります。`i` は曲の番号で、`seed` が 0 なら順番どおり、それ以外なら毎回同じ
  順番でシャッフルします。曲が終わる前に、スキルが次の曲（`i + 1`）をキューに入れます。
- Voynix は、プレイリストを探し（大文字小文字、全角半角、ひらがな／カタカナの違いは吸収）、署名と期限を確認し、
  Echo が再生できない形式なら `afconvert` で AAC に変換して（Echo は MP3 と AAC だけ）、Range 付きで配信します。
  家の中（プライベートアドレス）以外からの接続は断ります。
- **なぜスプリット DNS なのか。** Alexa のクラウドは、再生指示の URL のホスト名がプライベート IP に解決されると
  拒否します（`INVALID_RESPONSE: The URL specified in the Play directive is invalid`）。一方、Echo は Mac に LAN 内の
  IP でしか届きません。そこで、ホスト名は、Alexa のクラウドを含めて**公開 IP** に解決させ、**Echo だけ**、自分で
  動かす DNS で Mac の LAN 内 IP に解決させます。

## 必要なもの

- Echo で聞きたいときに、起きていて Voynix が動いている Mac（Mac がスリープすると、Echo の名前解決もできなくなります。
  [制限](#制限) を参照）。
- 端末ごとに DNS を指定できるルーター（たとえば ASUS: LAN → DHCP サーバー → 固定割当の「DNS サーバー」欄）と、
  IP を固定した Echo。
- DNS を自分で操作できるホスト名と、その公的な認証局の証明書。無料の [DuckDNS](https://www.duckdns.org/)
  （`<名前>.duckdns.org`）でも、自分のドメインのサブドメインでも構いません。
- **Echo を登録しているのと同じ Amazon アカウント**の開発者アカウント（日本なら amazon.co.jp）。別のアカウントで
  作ったスキルは、Echo には出てきません。
- `brew install lego dnsmasq`、Node.js 18 以上（スキルのテストを動かす場合のみ。任意）。

## 1. ホスト名と証明書

1. ホスト名を作ります（DuckDNS: `<名前>` を追加し、「current ip」には**適当な公開 IP**（例: `1.1.1.1`）を入れます）。
   Alexa のクラウドは、それがプライベートでないことだけを見ます。DuckDNS の token は控えて、チャットや git には
   出さないでください（`~/.duckdns-token`、権限 600 がおすすめです）。
2. DNS-01 で Let's Encrypt の証明書を取ります（Mac がインターネットから見えている必要はありません）。

   ```sh
   DUCKDNS_TOKEN=$(cat ~/.duckdns-token) lego run --path ~/.lego --email you@example.com --accept-tos \
     --dns duckdns --domains <名前>.duckdns.org
   ```

   できるファイル: `~/.lego/certificates/<名前>.duckdns.org.crt`（フルチェーン）と `….key`。中間証明書まで入って
   いるか確認してください（Echo は不完全なチェーンを受け付けません）。

   ```sh
   openssl crl2pkcs7 -nocrl -certfile ~/.lego/certificates/<名前>.duckdns.org.crt \
     | openssl pkcs7 -print_certs -noout | grep subject      # 2 行以上出れば OK
   ```

3. 証明書は 90 日で切れます。残り 30 日以下になったら更新する週 1 回のチェックを入れます（LaunchAgent、`sudo` 不要。
   手順 1 の DuckDNS の token ファイルを使います）。

   ```sh
   scripts/echo-lan/echo-lan.sh cert <名前>.duckdns.org you@example.com    # token が ~/.duckdns-token でなければ、最後にファイルのパスを付ける
   launchctl kickstart gui/$(id -u)/com.voynix.echo-cert-renew; tail ~/.lego/renew.log   # 今すぐ 1 回動かす。「Skip renewal」と出れば正常
   ```

   毎週月曜の 04:17 に動き（その時刻に Mac が寝ていれば、復帰後）、ログは `~/.lego/renew.log` に出ます。書き換えられた
   証明書は、Voynix が数秒で自分で読み直すので、再起動は要りません。更新に失敗してもログに理由が残り、古い証明書は
   期限まで使えます。（DuckDNS 以外の DNS は、自分のジョブで `lego run … --dns <プロバイダー> --renew-days 30` を
   動かしてください。）

## 2. Echo 専用の DNS

ルーターで、Mac の LAN 内 IP を固定（DHCP の予約）にしてから、小さな dnsmasq を入れます。ホスト名にはその IP を
返し、それ以外はルーターに転送します。

```sh
scripts/echo-lan/echo-lan.sh --dry-run dns <名前>.duckdns.org <Mac の LAN IP>   # 書き込む内容を表示するだけ
scripts/echo-lan/echo-lan.sh dns <名前>.duckdns.org <Mac の LAN IP>
dig +short <名前>.duckdns.org @<Mac の LAN IP>      # → Mac の LAN IP
dig +short example.com @<Mac の LAN IP>              # → 本物の答え（転送されている）
```

LaunchDaemon として動きます（53 番ポートは root が要るため）。Laravel Valet の dnsmasq は 127.0.0.1 だけで待ち受けるので、
衝突しません。

次に、**ルーターで、Echo だけをこの DNS に向けます。** ASUS（純正ファーム）: LAN → DHCP サーバー → 固定割当で、Echo
（クライアント一覧から選択）、その IP、DNS サーバー = Mac の LAN IP を入れて追加し、「Advertise router's IP in addition
to user-specified DNS」を**「いいえ」**にして、適用します。WAN 側の「DNS サーバー／アサイン」の画面は、ルーター自身の
上流の DNS なので使いません。そのあと Echo を再起動して、リースを取り直させます。ほかのルーターは、端末ごとの
DNS 指定の機能を探してください。

Echo がこの DNS を使っているかの確認（任意）: インストールした dnsmasq は、問い合わせを記録しません。1 分だけ見るには、
いったんデーモンを止め、記録つきで前面で動かし、Echo を再起動して、Echo の IP が Amazon の名前を引いていることを
確認します（Ctrl-C のあと、デーモンを戻します）。

```sh
sudo launchctl bootout system /Library/LaunchDaemons/com.voynix.echo-dns.plist
sudo dnsmasq --no-daemon --log-queries --conf-file=/opt/homebrew/etc/voynix-echo-dnsmasq.conf   # パスはスクリプトの出力に出ます
sudo launchctl bootstrap system /Library/LaunchDaemons/com.voynix.echo-dns.plist
```

## 3. 443 番を Voynix に転送する

Echo は 443 番にしか接続しませんが、普通のアプリは 443 番を使えません。Voynix は **8443 番**で待ち受け、`pf` のルールで、
Mac 自身の LAN アドレスの 443 番を 8443 番に転送します。

```sh
scripts/echo-lan/echo-lan.sh --dry-run pf <Mac の LAN IP>
scripts/echo-lan/echo-lan.sh pf <Mac の LAN IP>
```

標準の `/etc/pf.conf` がもともと見ているアンカー（`com.apple/*`）にルールを入れるので、`/etc/pf.conf` は書き換えません。
起動時にも自動で入ります。Mac 自身からは、この転送を試せません。LAN 内の別の端末から `curl -vk https://<Mac の LAN IP>/play`
を実行して、TLS の接続まで進めば OK です（Voynix が 400／403 を返します）。

## 4. Voynix で有効にする

設定 → **Echo**:

1. 証明書（フルチェーン）と秘密鍵のパスを入力して、**「適用」**を押します（2つは同時に反映されます。新しい証明書に古い鍵
   だと読み込めないためです）。ポートは 8443 のままにします。
2. **「Echo 再生を有効にする」**にチェックを入れます。パスを入れる前にチェックすると「先に証明書と秘密鍵のファイルを
   指定してください」と出て、チェックが外れます。状態表示が「ポート 8443 で稼働中」になれば OK です。
3. **表示／コピー**で、スキルに入れる共有シークレットが取れます。再生成すると、古いシークレットと、すでに Echo に渡した
   リンクがすべて無効になるので、あとでスキルの `config.json` も更新してください。

Voynix の開発版も動かしている場合は、同時には動かさないでください（同じポートを使い、シークレットも別々に持っています）。

## 5. Alexa スキル

ソース: [`alexa-skill/`](../alexa-skill)（各ファイルの役割は、その README を参照）。Audio Player を使う、Alexa-hosted
（Node.js）のカスタムスキルです。`ja-JP.json` の呼び出し名は `ラジカセ` です。変えてもかまいませんが、「ミュージック」
「音楽」「プレイリスト」を含まず、英語に聞こえない普通の言葉にしてください（「マイミュージック」は Amazon Music に
取られます）。

1. **Echo と同じ Amazon アカウントを使います。** Alexa アプリの「その他 → 設定 → アカウント設定」で、Echo がどの
   アカウントのものかが分かります（日本なら、たいてい amazon.co.jp）。<https://developer.amazon.com/alexa/console/ask>
   に、**そのアカウント**でサインインします（開発者登録を求められたら登録します。無料です。審査や公開、本人確認は
   要りません。開発中のスキルは、同じアカウントの端末でだけ使えます）。コンソールは、**別の Amazon アカウントや
   別の地域に、勝手にサインインしていることがあります**。右上のアイコンのメニューで確認して、違えば、サインアウト
   して入り直してください。Alexa アプリの「マイスキル」には、開発中のスキルが出ないので、正しい場所かの確認には
   使えません。
   そのうえで、スキルの作成 → 名前は何でもよい、言語は日本語（JP）、タイプは**その他**、モデルは**カスタム**、
   ホスティングは **Alexa-hosted (Node.js)**、リージョンは**米国西部（オレゴン）**（米国東部は作成に失敗したことが
   あります）、テンプレートは**スクラッチで作成**。
2. ビルド → インターフェース → **Audio Player をオン** → 保存。
3. ビルド → 対話モデル → JSON エディター: `alexa-skill/skill-package/interactionModels/custom/ja-JP.json` を貼り付け
   → 保存 → **スキルをビルド**。「最後に成功したビルド」の時刻が新しくなるまで待ちます（保存だけでは反映されません）。
4. **プレイリスト名を Alexa に教えます。** これをしないと、音声認識が推測します（「ヒロト＆マーシー」が「廣戸麻生」に
   聞こえ、どれにも一致しませんでした）。Voynix の設定 → Echo の**「プレイリスト名をコピー」**を押し、JSON エディターで、
   モデルの `"types"` の `PLAYLIST` の項目を、コピーした内容に置き換えて、もう一度**スキルをビルド**します。
   プレイリストを増やしたり名前を変えたら、また行います。
   - **聞き間違いは、同義語で直します。** Alexa が間違った文字を返したら、その文字（と、もっと簡単な呼び名）を、その
     値の `"synonyms"` に足します。例: `"name": {"value": "ヒロト＆マーシー", "synonyms": ["ヒロト", "廣戸麻生", "仕事マーシー"]}`。
     Alexa が何と聞き取ったかは、コンソールの コードエディタ → **CloudWatch Logs** で、`REQUEST IntentRequest` を検索し、
     `{"playlist":"…"}` を見ます。`PLAY … list=…` の行で、正式なプレイリスト名なら一致しています。聞き取った文字
     そのまま（漢字が多い）なら、一致していません。人名は漢字の当て字が多いので、何度か繰り返すことになります。
   - **英語の名前は、そのカタカナとは別物です。** Voynix は大文字小文字、全角半角、かなの違いは吸収しますが、
     「For Drive」と「フォードライブ」は同じと見なしません。カタカナの読みを同義語に足してください。
5. コード: `lambda/package.json` と `lambda/index.js` を置き換え、`lambda/playback.js` を追加し、`config.example.json` から
   `lambda/config.json` を作ります（`baseUrl` = `https://<名前>.duckdns.org`、`secret` = Voynix のもの）→ **保存 →
   デプロイ**。デプロイが終わる（「最終デプロイ日時」が更新される）のを待ってから試します。
6. テストタブ → ステージを**開発中**にします。シミュレーターで「*〈呼び出し名〉* を開いて」と入力すると、どのプレイリストを
   かけるか聞かれます。続けて「*〈プレイリスト〉* をかけて」。JSON 出力に `AudioPlayer.Play` の指示があり、`url` が
   `https://<名前>.duckdns.org/play?list=…` になっていれば OK です。Echo には、「アレクサ、*〈呼び出し名〉* を開いて」
   と言い、聞き返されたら（ウェイクワードなしで）「*〈プレイリスト〉* をかけて」（シャッフルなら「…をシャッフルして」）。
   日本語では、呼び出し名のあとにつなぎの言葉が要ります: 「…を開いて」、または「…で、*〈プレイリスト〉* をかけて」。

コンソールに貼るファイルは、クリップボード経由にすると、シークレットが画面に出ません
（`pbcopy < alexa-skill/lambda/config.json`）。貼ったあとは、クリップボードを空にします（`pbcopy < /dev/null`）。

## Alexa 側でハマりやすいところ

- **シミュレーターが通っても、Echo で動くとは限りません。** シミュレーターは、コンソールにサインインしているアカウントの
  スキルを動かし、Echo は、Echo のアカウントのスキルを動かします。シミュレーターは新しい返事なのに、Echo では古い返事
  （または「お役に立てません」）になるときは、編集したスキルが、Echo とは別の Amazon アカウントのものです。
- **保存しただけでは反映されません。** モデルを変えたらビルドの完了を、コードを変えたら、保存してからデプロイの完了を
  待ちます。早く試すと、前のバージョンが動きます。
- **標準機能に似た名前は取られます。** 「マイミュージック」や、ミュージック／音楽／プレイリストを含む名前は Amazon
  Music に、造語は聞き間違えられます（「ボイニックス」は「v nex」になりました）。普通のカタカナ語にして、先に Alexa
  アプリの「Alexaに聞く」に文字で入力して、試してください。
- **日本語では、呼び出し名のあとにつなぎの言葉が要ります。** 「ラジカセ ヒロトをかけて」と続けて言っても、スキルとは
  認識されません。「ラジカセを開いて」のあとでプレイリスト名を言うか、「ラジカセで、ヒロトをかけて」と言います。
- **CloudWatch の画面の上の赤い「cloudwatch:GetMetricData を実行する権限がありません」は、無害です。** 下に出ている
  ログのイベントを見てください。

## 確認とトラブルシューティング

| 症状 | 見るところ |
|---|---|
| 「お役に立てません」／スキルが開かない | Amazon アカウントの違い（Echo のアカウント ≠ 開発者アカウント）、呼び出し名が標準機能に取られている・つなぎの言葉（「…を開いて」）がない、モデルをビルドしていない。Alexa アプリの「Alexaに聞く」に文字で入力して試す。 |
| Echo が、スキルの古い版（古い返事）を開く | コードを、Echo とは別の Amazon アカウントのスキルに貼った（シミュレーターは、コンソールのアカウントで動くので、通ってしまう）、またはデプロイが終わっていない。 |
| スキルは開くが、Echo が何も言わない／止まる | スキルの CloudWatch ログ（コンソール → コードエディタ → Logs）: `SESSION ENDED` に `INVALID_RESPONSE` なら、Alexa のクラウドが URL を拒否しています（ホスト名がクラウドからはプライベート IP に見えている。`dig +short <ホスト名> @1.1.1.1` で公開側のレコードを確認）。`PLAYBACK FAILED` にはエラーの種類が出ます。 |
| Echo の分の行が Voynix の出力にない | DNS: Echo の端末別 DNS の設定が反映されているか（Echo を再起動）、dnsmasq に、ホスト名を引く問い合わせが来ているか（手順 2）。 |
| Echo が接続するが TLS エラー | 証明書のチェーンが不完全、またはホスト名が証明書と違う。 |
| Voynix のログに 403 | 署名の期限切れ、またはシークレットの不一致（`config.json` の `secret` ≠ Voynix のもの）、または LAN 外からのリクエスト。 |
| 「プレイリストが見つかりません」の声が流れる | 言った名前がどれにも一致しなかった、またはプレイリストが空。スキルのログの `PLAY … list=…` で聞き取った文字を見て、漢字などの別の表記なら、プレイリスト名をモデルに同義語つきで足す（手順 5.4）。英語の名前には、カタカナの読みを同義語に足す。 |
| FLAC や ALAC で飛ぶ／無音 | `afconvert` がない、または最初の変換が遅い（曲の再生中に、次の曲を先に変換します）。 |

Voynix は、リクエストごとに 1 行、標準エラー出力に記録します（`echo /play <ip> i=… seed=… -> <status>`）。署名は
記録されません。

## 制限

- **Mac は起きている必要があります。** スリープや終了で、Echo は届かなくなり、Echo は Mac の DNS を使っているので、
  ほかの名前の解決も失敗します。困るなら、dnsmasq を常時動く機器（ラズパイ、NAS）に移して、Echo の DNS をそちらに
  向けてください。ほかは変わりません。
- DNS を向けた Echo だけが再生できます（ほかの Echo は、ホスト名を公開 IP に解決して失敗します）。
- ファイルがない（外したドライブなど）曲は飛ばし、同じ曲が 2 か所にあれば、存在するほうを再生します。変換できない
  形式の曲は、キューが止まります。
- リンクは、スキルが署名してから `ttlSeconds`（既定は 2 時間）の間だけ有効です。1 曲がそれより長い（オーディオブック、
  長いミックス）と、期限後に Echo が取り直したときに失敗することがあります。そういうファイルを聞くなら、スキルの
  `config.json` の `ttlSeconds` を増やしてください。
- 変換したファイルは、アプリのデータフォルダの `remote-cache/` にあり、30 日で削除されます。
- プレイリストの最後では、スキルがキューに入れた次の曲が 404 になり、Echo は止まります（ログに再生失敗が出ますが、
  想定どおりです）。
- 公開 DNS のレコードと証明書は公開情報です。見えるのはホスト名で、LAN 内の IP や音楽は見えません。

## 取り外し

`scripts/echo-lan/echo-lan.sh uninstall` で、DNS と転送の LaunchDaemon、週 1 回の証明書チェックを外します。そのあと、
ルーターから Echo の DNS 指定を外し、Voynix の設定のチェックを外し、Alexa のコンソールでスキルを削除します。

## セキュリティ

- サーバーは、プライベートアドレスからの接続だけを受け付け、`/play` だけを配信します。URL は 2 時間有効（スキルが設定）で、
  1 つのプレイリスト、曲番号、シャッフルの種に結びついています。
- 共有シークレットを知っている人は、あなたのネットワークから、Voynix に音楽を再生させられます（それ以上のことは
  できません）。Voynix のローカルの設定と、スキルの `config.json`（git 管理外）に保存され、バックアップには入りません。
  パスワードと同じに扱い、チャットには貼らないでください。
